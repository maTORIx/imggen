# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`imggen` is a Typer-based CLI wrapping Hugging Face `diffusers` for local image generation. It ships several backends ("kinds"): `sd` (SD1.5/SDXL/SD3.5), `qwen-image` and `qwen-image-edit` (Qwen-Image 20B, GGUF-quantizable), `see-through` (transparent/RGBA output via LayerDiffuse or BiRefNet matting, plus `--method decompose` for part-layer PSD export), and `background-removal` (standalone matting: Lucida / BiRefNet-HR / RMBG-1.4).

## Commands

The project uses **uv** (there is a `uv.lock`; `pip` alone will not pick up the pinned CUDA wheel index). There is **no test suite, linter, formatter, or CI configured** — do not invent `pytest`/`ruff`/`mypy` commands.

```bash
uv sync                              # install into .venv (pulls torch from the cu130 index)
uv run imggen version                # smoke test: prints version + device
uv run imggen <kind> -p "a red fox" --out fox.png   # generate (sd|qwen-image|qwen-image-edit|see-through)
uv run imggen qwen-image-edit -i in.png -p "make it snow"   # img2img/edit kinds need --init/-i
uv run imggen see-through --method decompose -i char.png -o char.psd   # face parts split, body merged -> one PSD
uv run imggen see-through --method decompose -i char.png -o char.psd --parts all   # every See-through part as its own layer
uv run imggen background-removal -i photo.jpg -o cutout.png        # RGBA cutout (default model: lucida)
uv run imggen background-removal -i photo.jpg -m birefnet-hr --mode mask -o matte.png   # the alpha alone
uv run imggen sd -i base.png -M cloth.png -p "..."                 # masked inpaint: only the white region may change
uv run imggen qwen-image-edit -i base.png -M face.png -p "..."     # masked edit: crops to the mask, blends back
uv run imggen parts masks base.psd -i base.png -o masks/           # decompose PSD -> clothing + face masks
uv run imggen parts extract base.png variant.png -o layer.png      # variant - base -> one RGBA layer
uv run imggen parts compose base.png layer_a.png layer_b.png -o out.png   # stack layers bottom-up
uv run imggen models [kind]          # list preset aliases (+ per-kind defaults); remote-aware (--local to force local)
uv run imggen pull [kind] --list     # list catalog presets published under models/ on GitHub
uv run imggen pull sd pony-diffusion-v6-xl   # install a catalog preset + download its weights now
uv run imggen samplers               # list --sampler aliases
uv run imggen init [--force]         # (re)seed ~/.config/imggen/settings with built-in presets
uv run imggen setup see-through      # pre-build the isolated env --method decompose needs (else built on first use)
uv run imggen serve [--host 0.0.0.0 --port 7863 --api-key KEY]   # run a generation daemon on this GPU host
uv run imggen remote set HOST[:PORT] [--api-key KEY]   # (client) route every generate through that daemon (PORT defaults to 7863)
uv run imggen remote status          # ping the configured remote (device/version)
uv run imggen remote clear           # forget the remote; run locally again
uv run imggen <kind> ... --local     # force local for one run even if a remote is set
```

Installed as a tool (`uv tool install git+...`), drop the `uv run` prefix. If not on CUDA 13.0, swap `pytorch-cu130` → the matching index in `pyproject.toml`.

## Architecture

End-to-end flow — the CLI never imports a backend; `GenRequest` is the only contract crossing the boundary:

```
cli.py (Typer)  ->  GenRequest (params.py)  ->  runner.run_and_save
  ->  pipelines/__init__.py::run   # single kind->backend switch, lazy imports
      # (remote configured? runner calls remote.run -> HTTP -> `imggen serve`
      #  -> pipelines.run on the GPU host -> same result list back)
        ->  <backend>.generate(req) -> list[(PIL.Image, metadata, path_hint)]
              ->  registry.resolve_model(kind, --model, token) -> ResolvedModel
                    ->  manifest.load_manifest / materialize   # JSON manifest -> download weights
              ->  common.py helpers (device, dtype, seeds, scheduler, placement)
  ->  imageio.build_output_paths + save_image   # PNG/JPG/WebP with embedded metadata
```

Key seams to understand before changing anything:

- **Backend contract is duck-typed, not an ABC.** Each `pipelines/<name>.py` exposes a module-level `generate(req, on_step=None) -> list[(image, dict, path_hint)]`. `path_hint` is `None` for a plain image, or `"fg"`/`"bg"` for see-through layer pairs (drives `_fg`/`_bg` output suffixes and forces `.png` for RGBA). Dispatch lives only in `pipelines/__init__.py::run`. `on_step(img_index, num_images, step, total)` is an optional per-denoise-step progress callback (NOT part of `GenRequest` — it can't cross the wire); backends attach it via `common.attach_progress` (a diffusers `callback_on_step_end`). Only `imggen serve` passes one, to stream progress to a remote client; local runs leave it `None` and rely on diffusers' own tqdm bar.

- **Image count vs batch are two axes.** `--num/-n` is the *total* image count; `--batch-size/-b` is how many run in one `pipe()` forward pass (`num_images_per_prompt`). `common.batches(seeds, gens, batch_size)` chunks the per-image seeds/generators so a backend loops `ceil(num/batch_size)` times, each call passing a length-B **list** of generators (one per image → each keeps its own consecutive seed) and `num_images_per_prompt=len(chunk)`. `batch_size=1` yields one image per pass — diffusers treats a 1-element generator list identically to a single generator, so the default path stays bit-for-bit with the old per-image loop. Wired in `sd.py` and `qwen.py` (both `generate`/`generate_edit`); **not `layerdiffuse.py`** — its transparent VAE decoder conditions per-sample and requires `num_images_per_prompt=1` (see `vendor/layer_diffuse/loaders.py`), so see-through's layerdiffuse path ignores `--batch-size` (the `matte` path batches for free via `sd.generate`). Caveat: batched forward-pass numerics differ slightly from single-image, so an image made at `-b>1` shares its seed's *pattern* but is not bit-identical to the same seed at `-b 1` (same property as A1111/ComfyUI batches); metadata records only the seed, not `batch_size`. Progress reports the batch's first image index (`on_step(base, num, …)`).

- **Remote execution reuses that same result seam.** `runner.run_and_save` calls `remote.run(req)` instead of `pipelines.run(req)` when a remote is configured (`imggen remote set`); both return the identical `list[(image, meta, hint)]`, so path building + saving stay client-side. `remote.py` (client) is stdlib-only and **must stay torch/diffusers/PIL-free at import** (PIL is lazy inside `run`) — it sits on the `cli.py` import path, same rule as `device.py`. `server.py` (`imggen serve`) is the heavy half: a stdlib `ThreadingHTTPServer` that re-runs `pipelines.run` behind a single generation lock, lazy-imported only by the `serve` command. **No fallback by design:** a configured-but-unreachable remote raises `remote.RemoteError` and the CLI exits non-zero (a 5s `/health` preflight makes that fast); `--local` forces local for one run. `--init` **and `--mask`** images are shipped inline (base64) and rehydrated to server temp files (`remote._INLINE_FILES`, wire keys `<field>_image`/`<field>_name`). Because `server._build_request` *drops unknown keys*, an old server would silently ignore a new field rather than fail — so `/health` advertises a `features` list and `remote._require_features` refuses to send `--mask` to a server that does not list it (a silently-unmasked edit looks plausible and is wrong). Add to both when adding a request field. The same function checks `req.kind` against `/health`'s `kinds`, so a backend the server predates fails immediately with a message that names it, instead of after the upload and the queue wait. `--model` is resolved on the *server*, so a client-local path only works if it exists on the server too. Because resolution is server-side, model *discovery* is too: the server exposes `GET /models` (`registry.models_info` → `{models: {kind: [{name, summary, gated, description}]}, defaults}`), and when a remote is configured both `imggen models [kind]` and `--model` shell completion query it (via `remote.models`) instead of listing local presets — so the aliases you see match what the server can actually load. `/health` and `/models` are the only GET routes; `/models` is gated by the api key when one is set. Config lives at `<config_home>/remote.json` (`$IMGGEN_REMOTE`/`$IMGGEN_API_KEY` override). **Progress streaming:** the client always POSTs `/generate` with `stream: true`; the server then responds with an NDJSON stream (`Content-Type: application/x-ndjson`, HTTP/1.0 connection-close framing) — per-step `{"event":"progress",step,total,image,images}` lines fed by the `on_step` callback, then a final `{"event":"result",results}` (or `{"event":"error"}`) line — and `runner._progress_reporter` renders a live bar client-side (TTY only). Backward-compatible both ways: a client detecting a non-NDJSON `Content-Type` parses the one-shot `{results}` body (old server), and an old server ignores the unknown `stream` key and returns `{results}` (the `_generate_once` path is still there).

- **Server keeps one model warm.** `common.cached_pipeline(key, build)` holds a single already-placed pipeline (LRU=1), gated by `$IMGGEN_PIPELINE_CACHE` which `serve` sets — so one-shot CLI runs are unaffected. Backends route load+`place` through it (`sd.py`, `qwen.py`); a different `--model` evicts the resident pipeline and frees CUDA memory before loading. Only load+placement is cached; the scheduler and per-call kwargs are re-applied every request.

- **`registry.py` is a *model* resolver, not a plugin registry.** `resolve_model` turns `--model` into a `ResolvedModel` with precedence: existing local path → manifest name (`settings/<kind>/<name>.json`) → raw HF repo id. `DEFAULT_MODEL` gives the per-kind default. Qwen single-file/GGUF transformers are wrapped in `SingleFileTransformer` (transformer loaded via `from_single_file`; text encoder/VAE/scheduler come from `base_repo`).

- **Shell completion is on** (`add_completion=True`). Value completers live in `cli.py` (`_complete_kind` / `_complete_sampler` / `_complete_model` / `_complete_catalog_alias`) and are attached via `autocompletion=` on the `pull` args and the shared `--model` / `--sampler` options. They run on every `<TAB>`, so they must stay fast: no torch, short network timeouts. To that end `device.py` imports torch **lazily** inside its functions (not at module top) — keep it that way, and don't add top-level torch/diffusers imports to any module on the `cli.py` import path, or completion and the light commands (`version`/`models`/`pull`/`samplers`) regress from ~30 ms to ~0.6 s.

- **`catalog.py` + `imggen pull` is the *install* path, distinct from resolution.** The repo-root `models/<kind>/<name>.json` tree is a public catalog served over HTTPS from GitHub (raw for a preset, the contents API for `--list`); `IMGGEN_CATALOG_DIR` reads a local tree instead (dev/testing), `IMGGEN_CATALOG_REPO`/`IMGGEN_CATALOG_REF` retarget the remote. `pull` copies the preset into the user settings dir **then downloads the weights via `manifest.materialize`; a download failure rolls the preset back** (nothing half-installed). Note `models/` is NOT packaged into the wheel — it's a GitHub-hosted catalog, only reachable once committed/pushed.

- **Manifests and presets are the same JSON schema** (`manifest.py` reads, `presets.py` writes). A manifest pins a `source` (`hf_repo` [+ optional `hf_file`], or a `url` — HF `resolve` URLs route through `hf_hub_download`, other URLs stream via `wget`) plus generation `defaults`. Saving a preset (`--save --alias`) writes an ordinary manifest, so recall is symmetric with any other `--model NAME`.

- **Setting precedence is centralized** in `common.py::setting(cli_value, key, defaults, fallback)`: explicit CLI flag > manifest `defaults[key]` > backend hardcoded `DEFAULTS`. Most `GenRequest` numeric fields default to `None` precisely so this rule works. Respect it — do not read CLI values directly in a backend. Positive-prompt templates (`defaults.prompt_prefix` / `prompt_suffix`, or `--prompt-prefix`/`--prompt-suffix`) are resolved the same way and applied via `common.compose_prompt` — the composed string is what's sent *and* recorded in metadata. Note: do **not** add a clip-skip setting for SDXL/Pony/Illustrious — diffusers already reads the penultimate CLIP layer for SDXL by default (== A1111 "clip skip 2"); passing `clip_skip=2` would wrongly index `hidden_states[-4]`.

- **Prompt weighting is ComfyUI/A1111 `(word:1.2)` markup, CLIP-only.** `common.apply_weighting(pipe, kwargs, prompt, negative)` swaps `prompt`/`negative_prompt` for weighted `prompt_embeds` (+ pooled for SDXL/SD3) **only when the composed prompt has an unescaped `(`/`[`** (`common.has_weight_markup`) — so plain prompts stay bit-for-bit on the normal encoder path. The embeds come from the **vendored** `src/imggen/vendor/sd_embed/` (subset of xhinker/sd_embed, Apache-2.0: `embedding_funcs` + the regex `parse_prompt_attention`; the heavy `lark`/`optimum-quanto`/Flux extras are omitted, so no new dependency). Pipeline family is picked by class name (`StableDiffusion3*` → sd3, `StableDiffusionXL*` → sdxl, else sd15); the sdxl/sd3 path uses the penultimate CLIP layer (matches the no-weight path, consistent with the clip-skip note above). The `sd` backend and `layerdiffuse` (SDXL) support it; **Qwen has an LLM text encoder with no standard token weighting, so `qwen.py::_strip_weights` drops the markup and warns** (`common.strip_weight_markup`). Weighting is applied to the *composed* prompt (after prefix/suffix), and metadata records `weighted: true`.

- **`see-through` composes the SD backend.** Its `matte` path re-dispatches through `sd.generate` via `replace(req, kind="sd")`; its presets are stored under the `sd` kind (`_preset_kind`); default model is `sdxl`. The `layerdiffuse` path uses vendored code under `src/imggen/vendor/layer_diffuse/` and hardcodes fp16.

- **`background-removal` (`pipelines/bgremove.py`) is the standalone matting kind, and its recipe comes from the model's *architecture*, not its preset name.** One image in (`--init`, required), one result out: RGBA cutout, or the 8-bit matte under `--mode mask` (`GenRequest.mode` is shared with see-through, so no new wire field). Three built-in presets, two families: `lucida` (default, `egeorcun/lucida`) and `birefnet-hr` (`ZhengPeng7/BiRefNet_HR`) are BiRefNet — ImageNet normalization, output is a list of logit maps whose **last** element is the finest, needs `.sigmoid()`; `rmbg-1.4` (`briaai/RMBG-1.4`) is BRIA's U²-Net — `[0.5]/[1.0]` normalization, output is `([sigmoid(d1..d6)], [features])` so the map is `out[0][0]` and is **already** a probability, plus a min-max stretch BRIA applies and BiRefNet does not. `_family()` dispatches on the loaded class (`BriaRMBG` → rmbg, else birefnet), like `common.weighted_embeddings` does for prompt weighting — so `-m briaai/RMBG-2.0` (a BiRefNet despite the name) lands on the right path. `--width`/`--height` are the **model's** input size (preset `defaults`: 1024, or 2048 for `birefnet-hr`), never the output size; the alpha is always resized back onto the input. Loading goes through `trust_remote_code` but resolves the class itself (`get_class_from_dynamic_module`) so it can set `all_tied_weights_keys = {}` on it: RMBG-1.4's repo code predates transformers 5 and never calls `post_init()`, so the Auto factory otherwise dies mid-checkpoint-load — a no-op for the BiRefNet models. fp32 by default (bf16 grains the matte); `--dtype` still wins. Loads route through `common.cached_pipeline`, so `imggen serve` keeps one matting model warm like any pipeline. Overlaps `see-through --method matte` on purpose: that one is a *stage* of transparent generation, this is the tool, and new matting models belong here.

- **`see-through --method decompose` is a subprocess, not an in-process backend.** It splits a character into semantic part layers (front/back hair, eyewhite/irides/eyelash/eyebrow, face, nose, mouth, ears, clothing — occluded regions **inpainted**, depth-ordered) and emits one layered `.psd`. **`--parts face` (the default) keeps only the head split** and collapses everything from the neck down into one `body` layer; `--parts all` is the raw ~20-part output. The merge is a second subprocess pass (`data/seethrough_merge.py`, run in the same isolated venv because rewriting a PSD needs `psd_tools`) that round-trips through See-through's own `psd2partdicts` → `dump_parts_psd`, so layer placement, depth sort and the `.psd.json` sidecar stay exactly as upstream would write them. Two things there are load-bearing: the keep-set regex needs **word boundaries** (a bare `ear` matches `handwear`/`footwear`/every `*wear` tag), and the merged layer takes the **minimum** `depth_median` of its members, not the median — it has to land where its front-most part was, or `back hair` pops out in front of the torso. It drives the See-through model (Lin et al., SIGGRAPH 2026, `shitagaki-lab/see-through`, Apache-2.0) — that stack pins `diffusers==0.37`/`transformers==5.0` and deep-subclasses diffusers internals, so it **cannot share imggen's process**; `_generate_decompose` runs its `inference/scripts/inference_psd.py` in an isolated venv. That venv is **auto-provisioned on first use** by `seethrough_env.ensure()` (stdlib-only, `git clone` → `uv venv` → `uv pip install` of the packaged pins in `data/seethrough-requirements.txt` → editable `repo/common`), landing in `~/.cache/imggen/seethrough/{repo,venv}` (follows `$IMGGEN_CACHE`); `imggen setup see-through [--force|--status]` is the same code path exposed for pre-warming. Treat it like any other first-run weight download — never make the user hand-build it. `$IMGGEN_SEETHROUGH_REPO`/`$IMGGEN_SEETHROUGH_PYTHON` point at an existing install instead (an explicitly-set-but-missing `PYTHON` is an error, not a cue to build one), `$IMGGEN_SEETHROUGH_AUTOSETUP=0` turns a missing env back into an error, and `$IMGGEN_TORCH_INDEX` retargets the CUDA wheel index (default cu130, matching `pyproject.toml`). Note the deps come from imggen's *packaged* pin list, not the checkout's `requirements.txt` — detectron2/mmcv/SAM2/GroundingDINO are data-pipeline tiers the PSD path never imports, and installing them is what makes the upstream setup miserable. Base image comes from `--init` or a fresh `sd.generate`. One PSD per run (`--num > 1` is ignored); `--width`/`--height` becomes See-through's `--resolution` (default 1280). ~6 min/image on GB10 with models cached.

- **Documents ride the wire as bytes, not as a path.** A backend that produced a real multi-layer file returns it as `meta["_psd_path"]` (a filesystem path) and `runner.run_and_save` `shutil.move`s it to `--out` — *consuming* the stash, so nothing leaks. That path is meaningless across the network, so `server._encode_result` **pops** `_psd_path`, ships the bytes as a base64 `psd` field next to the preview PNG, and unlinks its own copy; `remote._decode_results` re-stashes them via `_stash_psd` and repoints `meta["_psd_path"]` at the client temp file, so the save path is identical local vs remote. `--out x.psd` works because `.psd` is in `imageio._IMG_EXTS` (else it would be read as a directory). Two consequences: the **server** needs the isolated See-through install (its `RuntimeError` surfaces as a stream `error` event), and decompose emits no `on_step` — a remote client would sit silent for minutes, so `runner._progress_reporter` renders the server's one `{"event":"status","stage":"running"}` line as `running on remote ...` (the subprocess's own tqdm goes to the *server's* console).

- **`--mask` is a *guarantee*, not a hint, and the guarantee is made in pixel space.** `GenRequest.mask` / `mask_grow` / `mask_blur` mean "only these pixels may change". Latent masking alone does not deliver that: the pipeline round-trips the whole canvas through the VAE, so nominally-untouched pixels come back a few levels off everywhere — enough that an expression patch built against the base body no longer drops cleanly onto an outfit variant. So every masked path ends with `common.composite_masked(original, result, mask)`, which restores the original wherever the mask is black. Measured: face-region max difference **0** across outfit variants, which is the property the whole `parts` workflow rests on. Two backends, two shapes: `sd.py` switches to a diffusers `*InpaintPipeline` (`_SINGLE_FILE_PIPELINES` gained a third slot per architecture, indexed by `_TASK_SLOT`; ordinary 4-channel-UNet checkpoints are fine — diffusers falls back to masked latent blending, ComfyUI's `SetLatentNoiseMask`) with `strength` defaulting to **1.0** rather than 0.8, since a masked region is being replaced, not nudged. `qwen.py::generate_edit` instead crops to `common.mask_bbox` and edits *that* — Qwen-Image-Edit re-frames whatever it is handed (measured: head shifted +6/−14 px and scaled 2% on a full-body image, however emphatic the prompt), so the crop box is what pins the geometry; `_work_size` scales the crop to `_MASK_WORK_PX` (768 long side, /16) because Qwen goes soft on small inputs, and `_paste_back` scales the result into the box and blends. Do not "simplify" either backend by dropping the final composite.

- **`parts.py` + `imggen parts` is the layer workflow; it reads decompose PSDs as *regions*, never as pixels.** `build_masks` derives two masks from a `--method decompose` PSD and emits them in the **original image's** coordinates (See-through letterboxes into a `--resolution` square; `letterbox_box` undoes it). Never recompose a PSD to get pixels back: See-through's `common/utils/io_utils.py::load_part` drops any part whose mask lives only in the bottom/right 10% of the canvas, so a full-body figure loses its `footwear`. Three tag-set facts are load-bearing and were each a bug first: (a) `back hair` is **occlusion-completed behind the whole torso**, so subtracting it as "head" erases the body — only `back hair ∧ ¬body` is visible hair; (b) the `face` layer is the **head silhouette**, reaching under the hair, so using it directly as a face mask smears grey along the hairline — the recipe is `erode(face,16) ∪ dilate(eyes/nose/mouth/brows,10) − front hair`, then keep only connected components containing a feature; (c) anything not head-tagged and not back-hair *is* the body, which is what makes the same code work on `--parts face` PSDs (one merged `body` layer) and `--parts all` ones alike. `--fit wide` (default) masks everything below the neck **including the background** so voluminous outfits have room; the repainted background is then discarded by `extract_layer`, which intersects the base-vs-variant difference with the subject's alpha (`seethrough.foreground_alpha`, the same BiRefNet the `matte` method uses) and fills enclosed holes. That differencing is only sound *because* the inpaint path is byte-exact outside its mask — the two features are one design, not two.

- **Schedulers** (`schedulers.py`): short ComfyUI/A1111 names → diffusers scheduler classes, with auto-generated `_karras`/`_exponential`/`_beta` variants. `common.set_scheduler` warns and keeps the model default on an unknown/incompatible sampler rather than aborting. Flow-matching models (Qwen-Image, SD3.5) require `flowmatch`; classic samplers are for SD1.5/SDXL.

## Runtime state (outside the repo)

- Presets/manifests: `~/.config/imggen/settings/<kind>/<name>.json` (override with `$IMGGEN_HOME` or `$XDG_CONFIG_HOME`). Package-bundled built-ins live at `src/imggen/settings/` and are copied into the user dir on first use, never clobbering user edits. `manifest.ensure_seeded` also fills in an **entirely missing kind directory** on an existing install — that is what makes a kind added by a later version (its `DEFAULT_MODEL` is a preset name) resolve without the user running `imggen init` — while leaving presets they deleted inside an existing kind deleted.
- Weight cache for `url`-sourced models: `~/.cache/imggen/models/<kind>/` (`$IMGGEN_CACHE`). HF-sourced weights use the standard HF cache.
- Isolated See-through env (only for `--method decompose`): `~/.cache/imggen/seethrough/{repo,venv}` (~5 GB, `$IMGGEN_CACHE`), built on demand — see `seethrough_env.py`.
- Remote endpoint (client): `~/.config/imggen/remote.json` (`{endpoint, api_key?}`; `$IMGGEN_REMOTE`/`$IMGGEN_API_KEY` override). Absent → local execution.
- Gated models: `--hf-token` / `$HF_TOKEN` (also `HUGGING_FACE_HUB_TOKEN`, `HUGGINGFACE_TOKEN`).

## Hardware notes

Targets aarch64 + NVIDIA GB10 (Blackwell, sm_121), CUDA 13.0. `device.py` picks CUDA > MPS > CPU; default dtype is **bf16 on CUDA** (fp16 MPS, fp32 CPU). Only the ~20B Qwen transformer is GGUF-quantized — the rest of the pipeline stays full precision. On unified-memory hosts set `IMGGEN_SEQUENTIAL_OFFLOAD=1` for sequential CPU offload; `--offload` on CUDA uses model CPU offload.
